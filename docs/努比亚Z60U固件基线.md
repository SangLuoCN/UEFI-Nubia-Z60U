## 实机已确认事实

以下内容来自 2026 年 10 月 22 日 Z60 Ultra 进入 TWRP 后的只读采集：

- Android 设备标识为 pineapple，启动镜像型号为 NX721J，启动镜像设备代号为 PQ83A01。
- 启动链使用 Android Boot Image v4，vendor_boot 也是 v4；当前启动槽位为 _a。
- 当前启动选择为 dtb_idx=2 和 dtbo_idx=16。vendor boot 中包含四个 Pineapple 相关 DTB，不能直接把 dtb_idx 当成文件名。
- 实时设备树根兼容字符串包含 qcom,pineapple，根节点模型为 Qualcomm Pineapple MTP。实机 qcom,msm-id 为 0x22d/0x20000 和 0x241/0x20000，与 UEFI 仓库 Resources/DTBs/giulia.dts 完全一致，因此当前 SoC 基线按 SM8650 Lanai 处理。
- UFS 控制器为 1d84000.ufshc，UFS PHY 为 qcom,ufs-phy-qmp-v4-pineapple，状态均为 okay。
- GPU 节点为 qcom,kgsl-3d0@3d00000，兼容字符串包含 qcom,adreno-gpu-gen7-9-1；实时 DT 的芯片标识为 43 05 14 01，GMU、KGSL SMMU 和应用 SMMU 均已枚举。
- 实时 DRM 已启用 DSI 面板，面板节点为 BF068_RM692H0，活动模式为 1116x2480 的 60、90、120 Hz 命令模式。
- 实时触控节点位于 QUPv3 GENI SE1 -> SPI -> goodix-berlin@0，兼容字符串为 goodix,brl-d，固件和配置文件分别为 goodix_firmware_9916r.bin 与 goodix_cfg_group_9916r.bin。
- 触控 SPI 频率为 20 MHz；面板坐标上限、IRQ GPIO、复位 GPIO 和电源 GPIO 已记录在外部 DT 转储中。UEFI 第一阶段不依赖这个触控节点。
- 关键分区已完成只读备份和大小、哈希校验；没有读取整个 userdata，也没有执行分区写入、擦除或 GPT 修改。

## UEFI 基线选择

### 选择 giulia，不选择 nx729j

nx729j 是同厂 ZTE、同为 1116x2480 级别显示设备的参考包，但它使用 KailuaPkg 和 SM8550 配置。Z60U 的实时 DT 是 Pineapple，不能把 SM8550 的芯片地址、GPU 初始化、时钟或电源表直接套过来。

giulia 使用 LanaiPkg，对应 SM8650 家族，且其 MemoryMapLib 与 Z60U 实时 DT 在 RSRV0、XBL DT、AOP、SMEM、UEFI FD、UEFI 栈、Kernel、Display reserved 和 TZApps 等关键区域上逐项吻合。因此当前固件工程以 giulia 为芯片和内存布局基线，再单独建立 ZTE/NX721J 包。

### 二进制资源策略

第一阶段复用 Binaries/giulia 中已经存在的 SM8650 二进制驱动，包括 UFS、USB、芯片信息和显示相关模块。不能把这些文件复制到新的二进制目录，也不能把它们误标成 ZTE 专属资源；源码通过 Binaries/giulia 明确表达复用 SM8650 资源的事实。

当前 USE_CUSTOM_DISPLAY_DRIVER=0，优先使用 ABL 已经建立的 Simple Framebuffer。这样可以先验证 UEFI 菜单、GOP、DarwinBoot 载荷和 UFS，而不在第一轮同时引入未知的 Z60U DSI 面板 XML。

## 编译前验证顺序

1. 检查包内不再引用 giuliaPkg、OnePlus 机型字符串或 1264x2780 显示参数。
2. 检查 Include/APRIORI.inc、Include/DXE.inc 和 Include/RAW.inc 中的每个 Binaries/giulia/... 文件真实存在。
3. 检查 nx721j.dsc 的 LanaiPkg、内存库、配置库和 FD 配置路径。
4. 使用 UEFI 仓库的 build_uefi.py 进行第一次静态和固件构建；如果构建失败，先按缺失子模块、工具链和路径问题修复，不修改手机。
5. 从生成物中确认 UEFI FD、Android v4 boot 镜像和载荷分区位置，再进入实机临时启动阶段。

## 实机启动策略

只有在固件构建成功且生成物经过解包检查后，才从 TWRP 执行以下非破坏性流程：

1. 通过 adb reboot bootloader 进入 bootloader。
2. 只使用 fastboot boot 临时 boot 镜像，不使用 fastboot flash。
3. 观察是否能进入 UEFI、是否能保留屏幕输出、是否能枚举 UFS 和 USB。
4. 失败时回到 TWRP 读取日志和分区状态，不覆盖原厂 boot、vendor_boot、dtbo、recovery、modem、persist 或 UEFI 变量分区。

任何 userdata 写入、分区擦除、GPT 变更、永久刷写和删除 Android 的操作，都必须在得到用户针对该具体步骤的明确确认后执行。本阶段没有进行这些操作。

## 尚未确认的问题

- UEFI 源码已经按 giulia 的 msm-id 选择 SOC_TYPE=2；仍需在实机 UEFI 早期日志中验证芯片信息驱动没有报告更细的变体差异。
- UEFI 直接接管 ABL framebuffer 后的实际 GOP stride、像素格式和缓存属性。
- Binaries/giulia 的 UFS、USB、PMIC 和时钟驱动是否完全适配 ZTE 的固件表。
- Z60U BF068_RM692H0 是否需要专用 DSI XML；在 SimpleFb 第一阶段成功前不引入。
- Goodix 触控尚未进入 UEFI/XNU 驱动阶段，必须在 DarwinBoot/XNU 基线稳定后单独移植。
- GPU 实际驱动不属于 UEFI 首次启动验收项；GPU 需要在 XNU 的 KGSL、GMU、SMMU 和 Adreno 原生路径中单独验证。
